SOFTWARE ARCHITECTURE DOCUMENT (SAD)Plataforma Institucional de Campanha — Especificação TécnicaVersão: 1.0.0-PRODStatus: Em Desenvolvimento / NormativoCAPÍTULO 1: Princípios Arquiteturais e Diretrizes Técnicas1.1 Filosofia ArquiteturalA arquitetura do sistema adota o padrão Feature-Based (Domain-Driven Design Simplificado). A base de código é compartimentada em domínios de negócios isolados (ex: projects, gallery), garantindo baixo acoplamento e alta coesão.Server-First: O motor de renderização primário é o servidor. A execução de código no cliente (Browser) restringe-se estritamente aos nós folha da árvore de componentes que exijam interatividade de estado ou manipulação de DOM.Performance e SEO First: A aplicação atende aos critérios de Core Web Vitals da web moderna, garantindo indexação imediata por web crawlers sem dependência de hidratação cliente-side massiva.Agnosticismo de Marca (White-label Ready): A camada de apresentação consome exclusivamente tokens semânticos de estilização injetáveis, permitindo a personalização completa de identidade visual (paletas e tipografia) sem refatoração estrutural de código.1.2 Objetivos Técnicos Não-FuncionaisLCP (Largest Contentful Paint): $\le 1.8\text{s}$ no carregamento da dobra inicial (Hero).CLS (Cumulative Layout Shift): $\le 0.05$ em todas as rotas públicas.Segurança Zero-Trust na Borda: Interceptação de rotas administrativas via Middleware na Edge Network antes da computação de origem.1.3 Stack Tecnológica ├── app/                      # Camada de roteamento (App Router)
│   ├── (public)/             # Rotas de acesso público (SSR/ISR)
│   └── (cms)/                # Rotas protegidas do painel administrativo
├── config/                   # Configurações globais e variáveis de ambiente
├── features/                 # Domínios de negócio isolados
│   └── [feature-name]/       # (ex: projects, gallery, hero)
│       ├── components/       # Componentes visuais exclusivos do domínio
│       ├── actions/          # Server Actions para mutação de dados
│       ├── services/         # Camada de abstração de dados/APIs
│       ├── schemas/          # Validações de payload e tipagem local
│       └── types/            # Interfaces e contratos TypeScript do domínio
├── shared/                   # Recursos de uso universal cross-feature
│   ├── ui/                   # Componentes primitivos de interface
│   ├── animations/           # Variantes e configurações globais de animação
│   ├── providers/            # Contextos e wrappers globais de cliente
│   └── hooks/                # Hooks utilitários genéricos
└── middleware.ts             # Roteador de segurança e interceptação na Edge
2.2 Regras Estritas de Dependência (Boundaries)Para preservar a integridade arquitetural, as seguintes restrições de importação são aplicadas normativamente:Isolamento de Features: Uma feature (features/A/) nunca pode importar arquivos internos de outra feature (features/B/). Caso haja necessidade de compartilhamento, o componente, tipo ou função deve ser extraído para o diretório shared/.Independência de Serviços: Os componentes de UI pertencentes a uma feature não possuem permissão para importar clientes de banco de dados (supabase) ou SDKs de terceiros diretamente. A comunicação deve ocorrer exclusivamente por meio de Actions ou Services do próprio domínio.Restrição do diretório app/: O diretório app/ deve conter estritamente arquivos de roteamento (page.tsx, layout.tsx, loading.tsx, error.tsx). Nenhuma regra de negócio, componente de interface complexo ou serviço deve residir diretamente em app/.
